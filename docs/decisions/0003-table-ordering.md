# 0003: Ordering from the table (`/s/[token]`)

**Status:** Decided (2026-11-20), inside docs/decisions/0001 F5 to F7; made by the website developer, for the owner's review.

**Context:** The CMS prints `{websiteUrl}/s/{token}` on each table's QR code. The guest's page is phone first, from the prototype's `order.html`. The contract is ProBiz CMS 1.0.0 (`apps/api/src/ordering`, its docs/decisions/0052 and 0054 S6). The SDK has no ordering helpers, so the code uses `client.rest` with the `PublicOrdering*` types of `ApiComponents`.

## Decisions

| #   | Topic         | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1  | The page      | `src/app/s/[token]` is a root layout and a dynamic page (`force-dynamic`, `cache: "no-store"` through `cmsUncached`), `noindex, follow` in metadata and in an `X-Robots-Tag` header, `Cache-Control: no-store`, not in the sitemap. The basket is one client island (`ordering/order-app.tsx`) that gets the page's data as props, so the menu is in the first HTML. It has no site header or footer: it is the prototype's single column.                                                                                                                                                                                      |
| T2  | Language      | `?lang=` when the site has it, else the best of Accept-Language among the site's languages, else the API's default; the API says what it used (`page.locale`) and offers `page.languages`. A layout cannot read the query string, so the proxy hands it over in `x-site-search` for the `lang` of `<html>`. The language links are `?lang=`; the basket is kept in `sessionStorage` per table, so a switch keeps it.                                                                                                                                                                                                            |
| T3  | The proxy     | `/s/...` is answered by the proxy itself (no CMS redirect, 410 or page lookup there): `PROXY_HANDLED_PATHS` in `lib/reserved-paths.ts`. `s` is a reserved top-level path.                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| T4  | Invalid code  | Next cannot give a dynamic page a 404 status and its own body: `notFound()` answers 404 with an empty `__next_error__` shell, as found in docs/decisions/0002 (the 404 finding), also with a `not-found.tsx` at the segment or above. So the proxy asks the API (`ordering/table-check.ts`, 2 s timeout) and, only on `ORDERING_TABLE_NOT_FOUND`, rewrites to `/~order-invalid/<token>` with status 404, like `/missing`. A direct visit to that internal address (no `x-order-invalid`) is a plain 404. Anything else (slow API, 429, module off) goes on to the page. This reads the table page twice per visit (CMS gap G8). |
| T5  | Other states  | `MODULE_DISABLED`: a friendly "ordering is not available" page (status 200). API failures and 429 on the page read: "try again" page. A venue that is closed (`venue.openNow` false) is shown, with its hours, and ordering is disabled; an `ORDERING_CLOSED` answer closes it for the rest of the visit.                                                                                                                                                                                                                                                                                                                       |
| T6  | Calls         | The browser calls `PUBLIC_API_URL` directly (docs/decisions/0001 F7), with the SDK's typed client for the JSON calls (`ordering/guest-api.ts`) and `fetch` for the stream. `PUBLIC_API_URL` (default `API_URL`) is read on the server and passed as a prop, never `NEXT_PUBLIC`, so one image serves any install. It must be an address the guest's browser reaches; the CMS's CORS must allow `SITE_URL`. Only `itemKey`, `priceIndex` (several prices), `qty`, `note` and `locale` are sent.                                                                                                                                  |
| T7  | The secret    | `guestSecret` is kept in `localStorage` per order id, 12 hours (`ordering/secrets.ts`), removed on `NAPLACENA` and `OTKAZANA`, when expired and when the API says the order is not there. On load the page resumes the newest order of this table and opens its status.                                                                                                                                                                                                                                                                                                                                                         |
| T8  | Live status   | A `fetch` reader of the SSE stream with `X-Ordering-Secret` (`ordering/sse.ts`, `watch.ts`): on each `order.updated` the order is read (it has the items and the cancel reason). If the stream cannot be read or is cut before a final status, `GET /orders/:id` every 10 seconds (the sheet says so); both stop after a final status. No automatic stream reconnect: the poll is the fallback.                                                                                                                                                                                                                                 |
| T9  | Accessibility | Steppers are labelled groups with the item's name; the cart and the status are modal dialogs (focus in, Tab kept inside, Escape and backdrop close, focus returns, the page behind is `inert`); the toast and the status title are live regions; touch targets are 44 px.                                                                                                                                                                                                                                                                                                                                                       |
| T10 | Not drawn     | Item pictures, allergens and dietary marks of the ordering menu are in the API's answer but not drawn: the prototype's page is text only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## Consequences

- Install setting `PUBLIC_API_URL` (in `deploy/.env.example` with PR 5). On Bricks it is `https://api.bricks.ba`.
- The basket shows prices from the page for orientation; the API prices the order, so a price change ends in `ORDERING_PRICE_CHANGED`: the page is read again (`router.refresh()`), the basket keeps what still exists.
- Gaps G7 to G9 are in docs/decisions/0002.
